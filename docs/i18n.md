# i18n in the `app` console

The customer console ships in **English and Russian**. `admin/` is deliberately
English-only — see
[the ADR](superpowers/specs/2026-08-19-i18n-strategy-design.md) for why, and for
the reasoning behind everything below.

English-only covers what admin *computes* as well as what it says: a date, a
number and the order of a list are English whatever the operator's browser is
set to. See [Values](#values-dates-numbers-sizes).

## The one rule that explains the rest

**`en.json` is the source. Everything else is generated from it.**

You never write Russian by hand (though you may correct it — see below). You
write the English string, and `bun run i18n:sync` produces the translation.

A key that exists only in a component is not a key. `$t('hi_name')` with no
`hi_name` in any `en.json` renders the literal text `hi_name` to the user.

## Adding a string

```bash
# 1. add the English text to the slice's locale file
#    app/slices/<slice>/i18n/locales/en.json
#    { "list": { "title": "Agents" } }

# 2. use it in the template
#    {{ $t('list.title') }}

# 3. generate the translation and commit both files
bun run i18n:sync
```

`i18n:sync` only touches what drifted: it sends the missing and the outdated
keys to Claude, one request per slice, and leaves everything else alone. Running
it twice in a row is a no-op.

Editing an English string later marks it outdated, so the next sync retranslates
just that key.

## Conventions

**Templates call `$t`.** vue-i18n injects it into every component, so
`const { t } = useI18n()` is not needed and is not used anywhere in `app/`.
`useI18n()` remains only where a component needs the locale *itself* — the
switcher (`setLocale`), and handing the language to a pure utility. Dates and
numbers do not count: they go through `useFormat()`, see
[Values](#values-dates-numbers-sizes).

**Copy computed in script travels as a key, never as text.** Validation
messages, headings that depend on state, button labels that change while
pending:

```ts
const error = computed(() => (invalidEmail.value ? 'account.email_invalid' : null));
const titleKey = computed(() => (isRegister.value ? 'account.create_title' : 'account.welcome_title'));
```

```vue
<p v-if="error">{{ $t(error) }}</p>
<h1>{{ $t(titleKey) }}</h1>
```

Text inside branching logic is invisible to the extraction sweep and to the
checker — that is the whole reason for this rule.

**Keys** are `snake_case`, grouped under a feature object, at most two levels
deep: `chat.empty_title`. They live in the slice that renders them.

**Keys are global at runtime.** vue-i18n merges every slice into one scope, so
`app_name` defined in `common` works from any slice — do not duplicate shared
copy. Generic wording that several slices need (`relative_time.*`) belongs in
`common`.

**Placeholders are named**: `{name}`, `{count}`. Never positional — a translator
reorders words.

**`@` must be escaped.** vue-i18n reads a bare `@` as a reference to another
message, so `jane@example.com` fails the build. Write `jane{'@'}example.com`.

**Plurals use `|`.** English has three branches, Russian needs four (the rules
live in `app/slices/setup/i18n/i18n/i18n.config.ts`):

```json
"slots_free": "no slots free | {count} slot free | {count} slots free"
```

```vue
{{ $t('list.slots_free', { count: free }, free) }}
```

**A hand-corrected translation is never overwritten.** If the machine wording is
wrong, edit `ru.json` directly. `i18n:sync` adopts a translation it has not
recorded rather than replacing it; only a changed *English* source triggers a
retranslation.

## Values: dates, numbers, sizes

A translated label next to a date in the wrong language is still a broken
screen. Each console has **one format module**, in its `common` slice, and it is
the only place allowed to call `toLocale*String`, `Intl.*` or `localeCompare`.

| | `admin` | `app` |
|---|---|---|
| Language | English, fixed — whatever the browser says | the active language |
| Module | `admin/slices/common/utils/format.ts` | `app/slices/common/utils/format.ts` |
| In a component | import the function | `const format = useFormat()` |
| Relative time | `useRelativeTime()` | `relative_time.*` keys |
| What each kind looks like | [admin-format.md](../specs/018-english-admin-locale/contracts/admin-format.md) | [app-format.md](../specs/018-english-admin-locale/contracts/app-format.md) |

```ts
// admin — the language is not a parameter
import { formatDateTime } from '#common/utils/format';
formatDateTime(agent.lastSyncAt); // Aug 21, 2026, 00:46

// app — follows the switcher, without a reload
import { useFormat } from '#common/composables/useFormat';
const format = useFormat();
format.clock(message.ts); // 12:46 AM · 00:46
format.size(file.size);   // 5.9 MB · 5,9 МБ
```

**A kind of value that is not in the module gets a function there first.** It is
not formatted by hand in a component: that is how admin came to spell English
three ways and to show "21 авг., 00:46" to an operator with a Russian browser
(CLEAN-127).

**`useFormat()` reads the language when it is called.** Use it in the template
or inside a `computed`, and a language switch repaints the value. A string
formatted once and kept — in a `ref`, in a store — stays in the language it was
made in. That is why a notice in the `bridle` store carries `limitBytes: 10485760`
and not `limit: '10 MB'`: `noticeParams()` turns it into a size when it is shown.

**Units are keys.** The number is written in the language's own notation and the
unit comes from `unit.*` in `common`, so English stays the source here too.

**Values from a closed list are shown through a key**: an agent's status, a
proposal's mode, a role. A value the console does not know — the API can add one
— is shown as received rather than hidden behind "Unknown".

### What is never translated or reformatted

Text a console was handed rather than wrote:

- what a person or the agent wrote — messages, file names, agent names;
- what the server sent — a refusal reason, an error detail, **a log line**,
  including any timestamp inside it.

It is shown exactly as received, in both consoles and in every language. Someone
will search the logs for that sentence or read it to support, and a translated
copy matches nothing. A Russian screen can therefore carry an English sentence
from the server; the words the console puts around it are Russian.

What the console says *when the server sent nothing* is the console's own text
and is a key like any other: `account.error_network`, `chat.error_generic`.

## Adding a locale

Add it to `app/slices/setup/i18n/locales.ts`:

```ts
export const LOCALES = [
  { code: 'en' as const, file: 'en.json' },
  { code: 'ru' as const, file: 'ru.json' },
];
```

Every slice registers this list, so that is the only edit — then run
`bun run i18n:sync` to fill the new files. A locale declared without its file on
disk breaks the build, so sync before you build.

## Adding a slice

A slice needs an `i18n` block before it can hold copy:

```ts
import { LOCALES } from '../setup/i18n/locales';

export default defineNuxtConfig({
  modules: ['@nuxtjs/i18n'],
  i18n: { langDir: 'locales', locales: LOCALES },
});
```

## The commands

| | |
|---|---|
| `bun run i18n:sync` | Translates missing and outdated keys, drops keys English no longer has, adopts hand-written ones. Needs `CLAUDE_API_KEY` in `.env.project`, plus `CLAUDE_WORKSPACE_ID` if that key is identity-linked — such a key answers every request with a 400 naming `anthropic-workspace-id` until the workspace is set. |
| `bun run i18n:check` | Verifies only. No network, no API key. Runs in CI. |
| `bun run locale:check` | Verifies that every value takes its language from its console's rule. No network, no API key. Runs in CI. Covers `admin`, `app` and the tool files in `api`. |

The two checks answer different questions and neither replaces the other:
`i18n:check` asks whether every key exists in every language; `locale:check`
asks whether a date, a number or a piece of text could get its language from
the wrong place.

`i18n:check` fails on any of:

- **missing** — `en.json` has a key `ru.json` does not
- **stale** — the English text changed after the key was translated
- **unrecorded** — a translation exists that sync has never seen (run sync to adopt it)
- **orphaned** — `ru.json` still carries a key English dropped
- **unescaped `@`** — would break the production build
- **undefined usage** — a component calls `$t('some.key')` that no locale defines

Only literal keys can be checked for that last one. `$t(titleKey)` and
`` $t(`features.${k}_title`) `` are resolved at runtime, so the scan skips them —
which is another reason to keep computed keys inside a small, obvious set.

`locale:check` fails on any of:

| Rule | Where | A finding is |
|---|---|---|
| **L1** | `admin`, `app` | `toLocale*String(`, `Intl.*`, `localeCompare(`, `useTimeAgo*(`, `useDateFormat(` or `navigator.language` outside the console's format module |
| **L2** | `admin` | a letter from a script other than Latin, anywhere in the source |
| **L3** | `admin` | a locale file other than `en.json`, `detectBrowserLanguage`, or a language other than `en` in the i18n setup |
| **L4** | `api/src/**/*.tool.ts` | a letter from a script other than Latin in a tool's `title`, `template` or `description` — the admin tool catalog shows all three |
| **L5** | `app`, `.vue` | literal text in a template, or in a static `placeholder`, `title`, `aria-label`, `alt` or `label` |

Every finding names the file, the line and what to use instead.

The check decides by **where a call sits and what script a letter belongs to**,
never by what the text means. That keeps it a rule, and it sets its limits.
These it cannot see:

- **another language written in Latin letters** in `admin` — German, Spanish.
  Telling English from German is a judgment; review owns it.
- **a raw value rendered through an interpolation**, `{{ agent.status }}`. Show
  values from a closed list through a key (above).
- **a sentence chosen in script** and rendered through a variable. Copy decided
  in script travels as a key (above).

An exception is an entry in `scripts/locale-check.allow.json` with the file, the
rule and a reason — optionally the exact text, so that excusing `Enter` on a key
cap does not excuse the rest of the file. There is no inline "ignore next line":
an excuse written next to the code it excuses gets copied along with the code.
An entry that no longer excuses anything is itself a finding.

## Where it runs

In two places, and it needs both:

- [`ci.yaml`](../.github/workflows/ci.yaml) — every pull request and every push
  to `main`, both checks.
- [`build-images.yaml`](../.github/workflows/build-images.yaml) — the `i18n` job
  gates `build-app` and the `locale` job gates `build-admin` and `build-app`, so
  a failing check stops the image before it is built and deployed.

The second one is not redundant. The two workflows are independent: a push to
`main` starts both in parallel, and the deploy path never waits for CI. A
message that breaks the vue-i18n compiler would fail the Nuxt build inside
Docker on its own, but a stale translation or a key no locale defines builds
perfectly well and reaches users as raw key text — that is what the gate is for.

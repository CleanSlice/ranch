# i18n in the `app` console

The customer console ships in **English and Russian**. `admin/` is deliberately
English-only — see
[the ADR](superpowers/specs/2026-08-19-i18n-strategy-design.md) for why, and for
the reasoning behind everything below.

## The one rule that explains the rest

**`en.json` is the source. Everything else is generated from it.**

You never write Russian by hand (though you may correct it — see below). You
write the English string, and `bun run i18n:sync` produces the translation.

A key that exists only in a component is not a key. `$t('hi_name')` with no
`hi_name` in any `en.json` renders the literal text `hi_name` to the user.

## Adding a string

```bash
# 1. add the English text to the slice's locale file
#    app/slices/<slice>/i18n/locales/en.json
#    { "list": { "title": "Agents" } }

# 2. use it in the template
#    {{ $t('list.title') }}

# 3. generate the translation and commit both files
bun run i18n:sync
```

`i18n:sync` only touches what drifted: it sends the missing and the outdated
keys to Claude, one request per slice, and leaves everything else alone. Running
it twice in a row is a no-op.

Editing an English string later marks it outdated, so the next sync retranslates
just that key.

## Conventions

**Templates call `$t`.** vue-i18n injects it into every component, so
`const { t } = useI18n()` is not needed and is not used anywhere in `app/`.
`useI18n()` remains only where a component needs the locale *itself* — the
switcher (`setLocale`) and date formatting (`toLocaleString(locale.value)`).

**Copy computed in script travels as a key, never as text.** Validation
messages, headings that depend on state, button labels that change while
pending:

```ts
const error = computed(() => (invalidEmail.value ? 'account.email_invalid' : null));
const titleKey = computed(() => (isRegister.value ? 'account.create_title' : 'account.welcome_title'));
```

```vue
<p v-if="error">{{ $t(error) }}</p>
<h1>{{ $t(titleKey) }}</h1>
```

Text inside branching logic is invisible to the extraction sweep and to the
checker — that is the whole reason for this rule.

**Keys** are `snake_case`, grouped under a feature object, at most two levels
deep: `chat.empty_title`. They live in the slice that renders them.

**Keys are global at runtime.** vue-i18n merges every slice into one scope, so
`app_name` defined in `common` works from any slice — do not duplicate shared
copy. Generic wording that several slices need (`relative_time.*`) belongs in
`common`.

**Placeholders are named**: `{name}`, `{count}`. Never positional — a translator
reorders words.

**`@` must be escaped.** vue-i18n reads a bare `@` as a reference to another
message, so `jane@example.com` fails the build. Write `jane{'@'}example.com`.

**Plurals use `|`.** English has three branches, Russian needs four (the rules
live in `app/slices/setup/i18n/i18n/i18n.config.ts`):

```json
"slots_free": "no slots free | {count} slot free | {count} slots free"
```

```vue
{{ $t('list.slots_free', { count: free }, free) }}
```

**A hand-corrected translation is never overwritten.** If the machine wording is
wrong, edit `ru.json` directly. `i18n:sync` adopts a translation it has not
recorded rather than replacing it; only a changed *English* source triggers a
retranslation.

## Adding a locale

Add it to `app/slices/setup/i18n/locales.ts`:

```ts
export const LOCALES = [
  { code: 'en' as const, file: 'en.json' },
  { code: 'ru' as const, file: 'ru.json' },
];
```

Every slice registers this list, so that is the only edit — then run
`bun run i18n:sync` to fill the new files. A locale declared without its file on
disk breaks the build, so sync before you build.

## Adding a slice

A slice needs an `i18n` block before it can hold copy:

```ts
import { LOCALES } from '../setup/i18n/locales';

export default defineNuxtConfig({
  modules: ['@nuxtjs/i18n'],
  i18n: { langDir: 'locales', locales: LOCALES },
});
```

## The commands

| | |
|---|---|
| `bun run i18n:sync` | Translates missing and outdated keys, drops keys English no longer has, adopts hand-written ones. Needs `CLAUDE_API_KEY` in `.env.project`, plus `CLAUDE_WORKSPACE_ID` if that key is identity-linked — such a key answers every request with a 400 naming `anthropic-workspace-id` until the workspace is set. |
| `bun run i18n:check` | Verifies only. No network, no API key. Runs in CI. |

`i18n:check` fails on any of:

- **missing** — `en.json` has a key `ru.json` does not
- **stale** — the English text changed after the key was translated
- **unrecorded** — a translation exists that sync has never seen (run sync to adopt it)
- **orphaned** — `ru.json` still carries a key English dropped
- **unescaped `@`** — would break the production build
- **undefined usage** — a component calls `$t('some.key')` that no locale defines

Only literal keys can be checked for that last one. `$t(titleKey)` and
`` $t(`features.${k}_title`) `` are resolved at runtime, so the scan skips them —
which is another reason to keep computed keys inside a small, obvious set.

## Where it runs

In two places, and it needs both:

- [`ci.yaml`](../.github/workflows/ci.yaml) — every pull request and every push
  to `main`.
- [`build-images.yaml`](../.github/workflows/build-images.yaml) — the `i18n` job
  gates `build-app`, so a failing check stops the image before it is built and
  deployed.

The second one is not redundant. The two workflows are independent: a push to
`main` starts both in parallel, and the deploy path never waits for CI. A
message that breaks the vue-i18n compiler would fail the Nuxt build inside
Docker on its own, but a stale translation or a key no locale defines builds
perfectly well and reaches users as raw key text — that is what the gate is for.
